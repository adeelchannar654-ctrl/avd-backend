# AVD backend — deploy notes (draft, nothing deployed, nothing spent)

## Why this exists
2026-11-22, live tests on https://www.allvideodownloader.tech/:
- Fresh YouTube cookies in Vercel (replaced, redeployed Ready 3:27 PM PKT) — still 422 "requires login or cookies".
- Latest yt-dlp (commit cd1c5d3, deployed Ready 3:42 PM PKT) — still 422.
- Conclusion agreed with rehan: Vercel itself is the blocker. YouTube now wants
  a PO-token (proof-of-origin) from an always-running provider service, which
  cannot run inside Vercel serverless functions, and Vercel's datacenter IPs
  are heavily flagged. No more Vercel-side attempts.

## What is in this folder
- `Dockerfile` — one container: latest yt-dlp (pip) + bgutil POT plugin +
  bgutil POT provider server (Node, port 4416) + ffmpeg + `server.mjs`.
  The plugin finds the provider at the default http://127.0.0.1:4416 with no
  extra extractor arguments (per bgutil-ytdlp-pot-provider 1.3.0 docs).
- `server.mjs` — Node stdlib only. `POST /analyze {url}` returns the same
  fields as `getVideoBasicInfo` in `src/lib/yt-dlp.ts`; `POST /download
  {url, format, title}` streams the file back. Formats mirror the repo
  exactly (video-highest/1080p/720p/480p/360p, audio 128/192/320kbps).
  `GET /health` reports ok + whether cookies are present.
  Optional `x-avd-backend-key` header (BACKEND_KEY env) so the backend is
  not an open public downloader.
- `start.sh` — starts the POT provider, waits for it, then the API. Decodes
  COOKIES_FILE_CONTENT (base64) to /tmp/avd-cookies.txt mode 0600, exactly
  like the Vercel code does.
- `render.yaml` — Render Blueprint: free Docker web service, health check
  on /health, COOKIES_FILE_CONTENT + BACKEND_KEY as env vars (not in git).

## Deploy on Render free (the prove-it-first step, $0, no card)
1. Push this folder to a repo (or add it to the Viddownload repo — his call).
2. Render dashboard → New → Web Service → connect the repo → it picks up
   render.yaml (or choose Docker manually, Dockerfile in this folder).
3. Environment: set COOKIES_FILE_CONTENT to the SAME base64 value already
   in Vercel (fresh export from 2026-11-22 — do not re-export, do not paste
   it in chat or commit it). BACKEND_KEY is auto-generated by render.yaml;
   copy it for the Vercel side.
4. Deploy, wait for Live, then test from anywhere:
   `curl https://<service>.onrender.com/health`
   `curl -X POST https://<service>.onrender.com/analyze -H 'Content-Type: application/json' -H 'x-avd-backend-key: <key>' -d '{"url":"https://www.youtube.com/watch?v=aqz-KE-bpKQ"}'`
   A working answer returns title + duration (not 00:00) and no 422.
   First request after idle takes ~1 min (free tier wakes from sleep).

## Then repoint the Vercel site (small change, not done here)
- In the Vercel project add env vars: `AVD_BACKEND_URL` (the Render URL)
  and `AVD_BACKEND_KEY` (same key). In `src/app/api/analyze/route.ts` and
  `src/app/api/download/route.ts`, proxy to the backend instead of running
  yt-dlp locally. Keep the oEmbed fallback and the 422 messages as they are.
- The site stays on Vercel; only the download work moves.

## Honest caveats
- Render is ALSO a datacenter IP. This may still be blocked by YouTube —
  that is exactly what the free test is for: it costs $0 and proves it
  before any money is spent. If Render fails, the same container moves
  unchanged to Railway (~$5/mo, no sleep) or the Oracle Always Free VPS
  (residential-adjacent IP, already planned for WireGuard) — no rebuild.
- Free tier limits (Render docs, checked 2026-11-22): sleeps after 15 min
  idle, ~1 min wake; 512 MB RAM; 750 free instance-hours/month per
  workspace; 5 GB bandwidth/month. A 300s download fits inside one request;
  very long videos may hit Render's request timeout — test with the same
  short video first, then a longer one.
- Cookies expire. When they do, re-export (same incognito steps as
  2026-11-22) and replace COOKIES_FILE_CONTENT in Render, then redeploy.
- Never commit COOKIES_FILE_CONTENT or any cookies.txt. This folder
  contains none.
